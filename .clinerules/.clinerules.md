# Atlas Logistics - Cline Rules

## Project
Atlas Logistics Fleet & Transport Management System

Production domain: app.atlaslogistics.co.mw
Company website: https://atlaslogistics.co.mw/
Production OS: Ubuntu VPS
Production database: PostgreSQL
SSL: Let's Encrypt / Certbot

## Core Rules
- Investigate the existing repository before modifying code.
- Never guess database tables, columns, routes, permissions, workflows, or configuration.
- Prefer the smallest safe change that completely solves the requirement.
- Preserve existing business logic, data, routes, permissions, workflows, and UI conventions.
- Never refactor unrelated code.
- Never claim a task, test, deployment, SSL installation, migration, or email configuration succeeded unless verified.

## Technology

- Respect the existing framework and dependency versions.

## Database
All schema changes must use migrations.
Use foreign keys, unique constraints, indexes, transactions, and appropriate decimal precision.

Before adding a table:
- Search for an existing equivalent.
- Check whether an existing table can be extended.
- Verify relationships.

Before adding a column:
- Search the repository.
- Inspect migrations, models, validation, API resources, and forms.

Never run destructive production SQL automatically.

Never automatically run:
- DROP DATABASE
- DROP TABLE
- TRUNCATE
- Mass DELETE
- Production reset

unless explicitly requested and understood.

## Security
Protect against:
- SQL injection
- XSS
- CSRF
- Mass assignment
- IDOR
- Broken access control
- File upload vulnerabilities
- Session attacks
- Brute force
- Sensitive information exposure

Backend validation is mandatory.
Use framework-supported password hashing.
Never store plaintext passwords.
Never log passwords or secrets.

## API
If an API exists:
- Version it where appropriate.
- Authenticate requests.
- Authorize requests.
- Validate inputs.
- Rate-limit sensitive endpoints where appropriate.
- Return consistent responses.
- Never expose stack traces or secrets.

## Performance
Avoid N+1 queries.
Use eager loading, indexes, pagination, and appropriate query optimization.
Use caching only where invalidation is understood.
Use queues for long-running work such as emails, exports, notifications, and heavy reports.

## Debugging
When a bug is reported:
1. Reproduce it.
2. Inspect logs.
3. Inspect database state.
4. Trace the request.
5. Identify root cause.
6. Fix the root cause.
7. Add/update regression coverage.
8. Re-test.
9. Report the actual cause.

Do not hide symptoms with arbitrary conditionals.

## AI Workflow
For every development task:
1. Understand the requirement.
2. Inspect the repository.
3. Identify affected modules.
4. Inspect database structure.
5. Inspect routes/controllers/models/services.
6. Plan the smallest safe implementation.
7. Implement.
8. Run appropriate checks/tests.
9. Inspect the final diff.
10. Update memory-bank documentation if required.
11. Report exactly what changed and what was verified.
